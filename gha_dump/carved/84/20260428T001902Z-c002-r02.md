We got close here, but assumptions about `Edges` & `Vertices` had us thrown for a while
`PortalEdges` do index `PortalVertices`, but Portals actually index both `Portal*References` lumps.

Basically, a `Portal` can be expressed as a loop of `Vertices` or `Edges`
`PortalVertexEges` & `PortalEdgeIntersect*` lumps are tables describing relations between forms.

`Portal -> PortalVertexReference -> PortalVertex` gives a nice clean polygon.
`Portal -> PortalEdgeReference -> PortalEdge -> PortalEdge` is really messy.
This is because `PortalEdge`s are shared across multiple `Portals` & can exceed their bounds.

Here's a diagram of `r1/mp_angel_city`'s `Portal[0]`:

Now, `PortalEdgeReferences` only index one end of each edge
So, we're using the `PortalVertexReferences -> PortalVertex` loop as our other endpoint
When you correctly visualise the location of each point, you can see that `PortalEdges` enclose the same winding as `PortalVertices` (`1 > 2 > 3 > 4`)

> Most `PortalVertexReferences` start from index 1, `PortalVertices[0]` is always `(0, 0, 0)`
